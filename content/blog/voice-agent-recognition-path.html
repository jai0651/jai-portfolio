I built a voice agent without calling anyone's API: noise suppression, voice activity detection, turn detection, speech recognition, and the pipeline that holds them together, each one written in PyTorch and each one sitting behind the same interface as the production model it is meant to be compared against.

The models were never the point. They exist to be understood and then replaced. What I actually came away with is a catalogue of specific, measured failures, and most of them were not failures of machine learning. They were failures of measurement.

This post covers the half of the loop that listens. A second post covers the half that talks.

1Four problems wearing one coat

It is tempting to read that row of boxes as one pipeline doing one job. It is not. Denoising is signal processing. VAD is binary classification. Endpointing is policy and contains no model at all. Recognition is sequence transduction with an alignment problem underneath it.

Knowing which kind of problem you are looking at is most of knowing which tools apply, and every time I got stuck it was because I had reached for the tool that belonged to a neighbouring box.

2The VAD is a data problem in a model's clothing

The voice activity detector is 55,000 parameters, which is small enough that you stop being able to blame the architecture. Mine was confidently wrong in the most ordinary condition there is: on room noise with nobody speaking, it reported P(speech) = 1.0.

Same architecture, same training loop, corrected training data, and the same input now scores 0.04. The model was fine. What it had been shown was not.

The cheapest thing I did all project Before training the VAD I wrote an evaluation set of the specific things I expected to break it: digital silence, mains hum, babble, and speech recorded too quietly. It took ten minutes. It then decided which checkpoint shipped, because the best hard-case score was 0.806 at step 2750 while the final step of the run scored 0.699. Last is not best, and only a targeted eval set can tell you that.

3The stage with no model in it

Endpointing answers "have they finished talking?" and it is the one box in the diagram where adding a model would be a mistake. It is a state machine over VAD output with a hangover timer, and the interesting content is entirely in the policy: how long a pause has to run before it counts as a turn ending, and what happens to that threshold mid-sentence.

It also dictates the threading model for everything else. Barge-in means detecting speech while the agent is still talking. VAD is sub-millisecond so it can run inline, but recognition and synthesis take hundreds of milliseconds, and if either of them runs on the event loop the agent literally cannot hear you while it speaks. The architecture of the whole system falls out of that one requirement.

4The alignment problem, and the trick that dodges it

Here is the core difficulty of recognition. You have 400 audio frames and three characters, and nothing tells you which frames belong to which character. Hand-labelling that correspondence at scale is not an option.

CTC's answer is to refuse the question. Define a many-to-one collapse, merge repeats and drop blanks, then sum the probability of every frame labelling that collapses to the target sequence. A forward-backward recursion makes that sum tractable. The blank symbol does two separate jobs that are easy to conflate: it lets the model emit nothing at a frame it is unsure about, and it separates genuine repeats, because without a blank between them "hello" collapses to "helo".

The first recognizer, a BiGRU with a CTC head trained on real LibriSpeech, produced this:

Word error rate 1.076, which is worse than emitting nothing. The useful question is not "how do I make this better" but "what kind of wrong is this". The rhythm is roughly right and the syllable count is roughly right. What is missing is any notion that English words are a finite set. CTC assumes conditional independence between output frames given the audio, which is exactly a statement that it has no language model. The output is what acoustics sound like without one.

5The failure that does not appear in the loss

Then a run collapsed, and it took me longer than it should have to notice, because it collapsed into something that looks like health.

The model discovered that emitting blank on every single frame is a safe answer with a finite loss. All frames blank. Output entropy 0.82 out of a possible 6.93. Greedy decoding returns the empty string.

Why it hid The loss was flat at a plausible value, which reads as a plateau rather than a failure. Word error rate was pinned at 1.0, which is indistinguishable from a model that is merely early in training. Both of the numbers I was watching were blind to it, and they were blind in a way that looked like patience being required.

The fix is not a better loss curve, it is a different instrument. Blank fraction per frame is a signal specific to this failure mode, it costs one line to log, and it goes to 1.0 the moment the collapse starts. Every silent failure I hit afterwards followed the same pattern: the headline metric could not distinguish the failure from a normal stage of training, and something cheap and specific could.

Two more from the same family, both of which train happily while quietly discarding your work. PyTorch's CTC loss with zero_infinity=True substitutes a zero gradient when a target is longer than the encoder output, which makes the sample impossible rather than loud, so a bad vocabulary choice silently trains on a fraction of your data. And torch.cuda.is_available() returned True twice on machines where a convolution then failed, once on a CUDA 13 wheel against a CUDA 12 driver and once on cuDNN 9.20 against a 9.10 driver. Asking whether a capability exists is not the same as exercising it. The bootstrap now runs a real convolution and looks at the result.

6It was the warmup, not the vocabulary

After the collapse I had a confident theory: the subword vocabulary of 1024 was too large for the data, and the fix was to restart at 256. I was about to spend three days on it.

Instead I spent an hour reading the reference recipe. ESPnet uses 5,000 subwords on this same corpus and reaches 8.4% word error. The vocabulary was not the problem, and had I "fixed" it that way and had it happened to work, I would have learned something false and kept it permanently.

The actual cause was the learning rate schedule. My warmup was 1,500 steps against the reference's 15,000. Too fast a rise locks CTC into the all-blank minimum and it does not come back out. One hour of reading beat three days of guessing, which is the most repeatable lesson in the whole project.

Attention is the smallest learned part of it.

The two heads are there because each covers the other's structural weakness on one shared encoder. CTC is monotonic, cheap and streams trivially, and it has no language model, which is where "mianthes" comes from. An attention decoder has the language model and can also wander or loop, because nothing forces its attention to move forward. Running both makes the decoder's fluency available while CTC's monotonicity acts as a stabiliser.

8Streaming costs three percent

Making a Conformer stream takes two changes and it only works if you make both. Attention gets chunked masking, so a frame attends within its chunk plus some history. The depthwise convolution has to become causal, left-padded only, because otherwise it leaks roughly 15 frames of future context and the attention mask you carefully wrote is a fiction.

Train with the chunk size resampled every batch and one set of weights then serves every latency operating point. Measured cost on my data: word error goes from 0.607 to 0.627 for 640 ms of lookahead, about 3% relative.

That number is worth internalising. Streaming is usually discussed as a quality sacrifice. At this scale it is a rounding error, and the reason to pick an architecture that streams by construction is that retrofitting it later means changing the convolution, which means retraining.

9Two ways my evaluation lied to me

The held-out set shared 39 of 39 speakers with the training set. Every word error rate I had quoted was therefore speaker-dependent, optimistic, and not comparable with any published number. Held out has to mean held out along the axis you care about, and for recognition that axis is speakers, not utterances.

Checkpoint averaging then made the model worse, which surprised me because it is folklore that it helps: averaging the last five checkpoints gave 0.659 against a best single checkpoint of 0.612. The technique assumes the checkpoints being averaged orbit a single basin. Mine spanned a run that went from 0.86 to 0.61, so they were in different basins and the average sat between them. Now I average the best K by held-out word error and keep the result only if it wins.

10What the numbers are worth

Whisper base.en reaches 0.033 word error, against my 0.607. It also saw 680,000 hours of audio against my 100. That is a 165,000 times data advantage, and quoting my number next to theirs without that ratio would be dishonest.

The more useful version of the comparison is that "the gap is data" turns out to be false as a general claim. For the VAD the gap really was data, and fixing the data fixed the model. For synthesis it was architecture. For recognition it is data, architecture, recipe and inference all at once, and the only way I found out which was which was by changing one at a time and measuring.
