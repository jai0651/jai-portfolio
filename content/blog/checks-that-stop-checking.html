My test suite printed this while one of my pages was displaying another page's numbers:

47 Try it blocks checked, 0 problems

The chapter on diffusion caching had a Python snippet in it that sized a jitter buffer for a voice pipeline (pasted there by accident, by an agent working in the wrong file), and the caption underneath was still discussing cache hit rates that nothing on the page had produced. Green build. Every check ran and none of them had anything to say, because each one was doing exactly what I'd written it to do.

That's happened four times now on this project in about three weeks, across four different checks, and I found the fourth one this morning while writing this post. So I've stopped reading "the suite is green" as information, and started asking a narrower question about each check: can this thing still fail?

What's being checked

The site is KnowML, forty-one chapters on machine learning (thirty-seven of them a fortnight ago, so it grows). Most sections carry a small runnable Python snippet with a caption quoting what it printed ("the gradient comes out at 0.0089", that sort of thing). Those captions are the only real promise the site makes. If the number in the caption and the number the code prints drift apart, the page's wrong in a way no reader will ever catch, and neither will I.

So there's a checker (about a hundred lines of Python, no dependencies). One decision in it has paid for itself several times over: it reads the rendered HTML, not the scratch file the snippet was drafted in.

BLOCK = re.compile(
    r'<details class="tryit"[^>]*>\s*'
    ...
    r'<pre><code>(.*?)</code></pre>\s*'
    r'<div class="tryit-out">(.*?)</div>',
    re.DOTALL)

code = html.unescape(code_html)
r = subprocess.run([PY, "-c", code], capture_output=True, text=True)

Two copies of every snippet exist and only one of them goes to readers, so checking the draft would mean checking a file nobody visits. That much was obvious going in. What wasn't obvious is how a regex behaves when the markup shifts underneath it.

Zero isn't a passing score

I made the code blocks default to expanded, since collapsing the code on a page whose point is the code seemed like a strange choice. That's one attribute:

<details class="tryit" open>

My pattern matched <details class="tryit"> literally. After the change it matched nothing, anywhere, on any page. So the loop body never ran, the problem counter stayed where it started, and the script printed 0 Try it blocks checked, 0 problems and exited zero. If I hadn't read that line out of habit I'd have had a passing build over untested snippets for as long as it took a reader to complain.

Widening the regex is the boring half of the fix. Here's the half that does the work:

if total == 0:
    print("FAIL: found no Try it blocks at all — the pattern has drifted")
    sys.exit(1)

There've been Try it blocks on this site since chapter one. Finding none means the pattern drifted, not that the blocks went away. If your check walks a collection, it should know roughly how big that collection ought to be, print the size on every run (so it sits in the log where somebody might notice it move), and refuse to pass on an empty one.

Then I edited the pattern to something deliberately wrong and ran it. Exit 1, and the right message (the one about the pattern having drifted). That took maybe forty seconds, and it's the only reason I believe the guard works.

One-sided assertions

Each chapter's table of contents is a drawer: a thin rail of ticks down the right edge that slides open when your pointer gets near it. I wrote a headless browser test for it. It hovered the rail, waited for the transition, and asserted the panel was visible. Sounds fine, right?

Separately, chasing a mobile overflow bug, I ran git checkout -- assets/css/style.css to compare something against HEAD. My drawer CSS was still uncommitted at that moment. It went away. My next commit shipped the markup and the JavaScript with no styling at all, so on production the panel sat permanently open and the rail was still 264px wide.

Why the test didn't care With no drawer CSS the panel is visible all the time. So it's certainly visible on hover. That assertion was true, and it was true for the worst possible reason.

A one-sided assertion on a two-state component tells you nothing, and the state you forget to assert is probably the default one, the state a reader sees before they touch anything. My rewrite checks closed first: panel hidden before any interaction, rail collapsed to 60px or less, one tick per heading. Then hover, visible, inside the viewport. Then pointer away, hidden again.

It found a second real bug about a minute after I wrote it. Escape removed .is-open and handed focus back to the toggle button, and this selector put the panel straight back:

.tocd:focus-within .tocd-panel { /* open */ }

The toggle lives inside .tocd, so focusing it counted as focus inside the drawer. Scoping to .tocd-panel:focus-within fixed it. I wouldn't have caught that by hand, because by hand you press Escape and then click somewhere else, the toggle blurs, the panel hides, and it all looks correct.

Proxies come apart eventually

Back to that jitter buffer code sitting on the diffusion page. check-tryit.py did everything it'd been designed to do. It found 47 blocks, parsed them, ran them, and confirmed each one exited zero and printed something. All true. That voice snippet ran beautifully in the wrong chapter.

"Runs and prints something" was standing in for "this page is describing this output", and those two came apart the moment I had three agents drafting chapters into a shared scratch directory (my setup, not their fault), overwriting each other's files. A proxy holds until the specific thing that breaks it turns up. Then it keeps holding, silently, and that's the annoying part.

So I wrote a second checker that binds the caption to the code. Captions here mark a figure as coming from the output by wrapping it in <code>, so the rule falls out of the markup: every number in a <code> span inside a caption has to turn up in that snippet's stdout.

hay = re.findall(r"-?\d+(?:\.\d+)?", r.stdout + "\n" + code)
for n in nums:
    dp = len(n.split(".")[1]) if "." in n else 0
    if not any(round(h, dp) == float(n) for h in hayf):
        missing.append(n)

Two details in there cost me a couple of passes. Comparison is numeric and rounded to whatever precision the caption chose, because a caption writing 1.000 is describing precisely what numpy prints as 1., and a string match calls that a failure. And the haystack includes the snippet source, not only its output, since a caption sometimes quotes a constant the code takes as an input (a figure cited from a paper, say) and that's still anchored to something on the page.

Both of those started life as failures on pages that were correct. I loosened the checker instead of editing the pages, twice, and that's where this approach can quietly rot. Do it once too often and you're back to a check that passes on anything. I don't have a rule for when to stop. I just try to notice that I'm doing it.

Break it on purpose

A new check is code with no tests whose failure mode is silence. So how do you know it works? Before trusting the caption checker I put the original bug back: pasted chapter 39's jitter-buffer snippet into chapter 40's slot, the same way the agents had done it by accident, and ran both scripts.

With the snippet swappedWhat it said
check-tryit.py47 Try it blocks checked, 0 problems
check-tryit-figures.pynamed all four orphaned figures, by page and by number

That's the entire verification and it takes a minute. Skip it and you've got a script that's never once been observed doing its job.

And then this morning

Writing this post, I went to re-run everything so I could quote real numbers, and got 39 failures (every snippet that imports numpy, more or less). All of them ModuleNotFoundError: No module named 'numpy'. That virtualenv (the one these snippets execute in) lived in /tmp, and macOS had apparently cleaned part of it out from under me.

Fine, rebuild it. But look at what the two checkers did when that interpreter was missing entirely:

if not os.path.exists(PY):
    print(f"SKIP: {PY} not found"); return 0        # caption checker

if not os.path.exists(PY):
    print("  SKIP %s: not found" % tag); continue   # per block, then exit 0

So npm run test:code on a machine where /tmp had been emptied would report 47 Try it blocks checked and executed, 0 problems having executed nothing at all, and the caption checker would print a single SKIP line and exit zero. It's the first bug again, and it'd been sitting there the entire time I was being pleased with myself about the first bug. The venv lives in the repo now (gitignored, one npm script to build it), and a missing interpreter's a failure:

$ TRYIT_PY=/nope/python python3 scripts/check-tryit-figures.py
FAIL: no interpreter at /nope/python — no caption would be cross-checked.
exit=1

Suspect the measurement

One more, from a tool that's got nothing to do with this project, because it's the sneakiest version of the same thing.

I've got a script that scores prose for whether it reads as machine-written, counting things like contractions per 100 sentences against a corpus of human engineering posts from 2015 to 2021. It reported the human posts at 24 contractions per 100 sentences. Generated prose sits around 3 to 6 (the four AI-written posts I measured ranged 2.5 to 6.2), so 24 is uncomfortably close, and I nearly threw the metric out as useless. Why would ten hand-written posts cluster that near the machines?

They don't. It was decoding &#39; to a space before counting, so every contraction on an entity-encoded page had vanished. The real figure is 62, and that axis turned out to be the sharpest single signal in the set.

When a measurement tells you the world looks much worse than you expected, suspect the measurement first. A broken check and a check delivering bad news look identical from outside.

What I still don't have

There's 42 to 144px of horizontal overflow on chapter pages at 390px wide. It predates all of this, it's identical at HEAD, and I've ruled out the display math, the inline math, the inline code and the drawer. I don't know what causes it, and there's no check for it, which is the honest summary of this suite: it verifies the things I already thought to worry about.

All four failures did share one property, though, and it's a cheap thing to look for. In each case the check reported a number, and the number was wrong in the direction that reads as success. Zero blocks instead of 36 (there were 36 at the time, 47 now). Visible on hover, with nothing said about hidden when not. 47 checked and 0 problems on a page quoting figures it never computed. 47 executed, none executed.

Every check here prints its denominator now, and I've broken each one on purpose at least once to watch it fail. check-tryit-figures.py cross-checks 47 captions against real output. If that number drops and I haven't deleted anything, something's drifted, and I'd rather hear it from the log than from a reader.
